# pdf-triptych

> 把一份读不动的标准 / 规范 / 白皮书，拆成一页能讲、能评审、能贴进汇报的图。不是"PDF 转图片"，是**先把藏在字里的结构挖出来，再决定用什么形状承载**。

---

## 为什么需要它

长标准文档读不动，不是因为字多，是因为**结构藏在字里**。

哪些是主线、哪些是横切、哪些只是用法，原文往往不说。ISO 标准尤其如此——它给你一堆并列的条款，却不告诉你条款之间是什么关系。于是你读完了每一节，仍然讲不清这份文档到底在说什么。

直接让 AI"把 PDF 转成图"，得到的是一堆罗列的方框：原文有几节就画几个框，看起来像结构图，其实只是目录换了个样子。

`pdf-triptych` 的回答：**结构不是画出来的，是读出来的。** 先派一个 agent 通读全文把结构挖出来，再把结构翻译成视觉通道，最后才写代码。

## 三张图，有递进也有共同标尺

| 图 | 讲什么 | 与上一张的关系 |
|---|---|---|
| 一 · 骨架 | 这份文档的层级结构：从抽象到具体怎么展开，哪些定义横跨若干层，有没有第三维度 | — |
| 二 · 细节 | 概念之间的准确关系，通常是把原文里的几张 figure 揉成一张 | 与图一**同轴叠放**：图二的每个框落在图一的哪一列，就属于哪一层 |
| 三 · 例子 | 换成一个具体场景，每样东西落在哪一列 | 与图一**同列**：沿竖虚线往上看就知道它对应结构的哪一层 |

共同标尺有两样，缺一不可：**贯穿全图的竖向虚线（列）** 和 **全文统一的三类颜色**。

张数由文档结构决定，不写死三张：原文 figure 之间有主从关系就分开画，互不相交就合成一张。

## 核心洞察

**1. 只读局部一定会读错层级。** 层级关系是这类图最核心的断言，也最容易读反——并列的分类句会被当成父子关系，"可以"会被读成"必须"。所以结构探针必须派 subagent 通读全文，且必须要原文的英文短句作为连接证据，不接受概括。

**2. figure 必须用眼睛看，不能读文本层。** 原文的图在 `pdftotext` 输出里只剩一行图题，框名、箭头方向、箭头上的文字、图例分组全都丢了。而图二基本就是在重画这些 figure——看不到图就只能瞎编。

**3. 先定视觉逻辑，再选形。** 把内容结构拆成"表达需求"，每个需求配一条**独立的视觉通道**，通道撞车图就乱。金字塔表达的是漏斗与转化，不是逐层展开——形状本身携带语义，选错了文案救不回来。

**4. 融合不是提炼。** 用户选中两个方案要合并时，任何以"其实已经包含了"开头的理由，都要先回去数一遍对方有几个框。正确做法是同轴叠放：两者完整保留，重排列宽让它们共用同一根横轴。

**5. 共同标尺是契约，违反就是撒谎。** 有了列，**任何元素的横向跨度都在向读者宣称"我属于这些列"**。跨度与真实归属不符，和柱状图断轴是同一类错误。所以横向区块一律走 `place()`，列归属不声明直接抛错——让声明成为书写时绕不过去的动作，而不是写在文档里的承诺。

## 怎么用

```bash
# Claude Code / Codex 里直接说
/pdf-triptych input.pdf
把这份 PDF 画成骨架图
```

六个阶段，每个阶段都有明确产出和验证：

```
0 提取      pdftotext 取正文；figure 用 Read 工具直接看图
1 结构探针   派 opus subagent 通读全文（六问模板，不可跳过）
2 视觉逻辑   把结构翻译成表达需求 × 视觉通道（不写代码，先给人看）
3 方案并置   3–4 个方案同页，各带长处短处，让人选
4 融合对齐   同轴叠放，定一组列 X[]，横向区块走 place() 声明归属
5 视觉打磨   纯视觉 review → 颜色 → 去决策过程措辞
6 例子层     同一组列换成具体场景，自下而上读
```

## 自带检查

```bash
python3 scripts/render_check.py out.html
```

一条命令做五件事：

- **自动测量页面真实高度**——不用手猜，猜大了截图一半空白会被误读成排版有问题
- `node --check` 语法
- 抓 Chrome console 的运行时错误——语法过不代表能跑，`const` 的暂时性死区是运行时才触发的
- 页面内自检：文字溢出画布 / 同行重叠 / 字号低于 8.4px
- **列归属检查**：从竖虚线本身推断列位置（只认长度超过画布 30% 的长线，短的是刻度或装饰），扫出所有横跨多列却没声明归属的区块

脚本本身经过对抗测试：人造一个带重叠、溢出、6px 小字的页面，三类问题都能抓到。

## 致谢

视觉取向受 **[lieflat-charts](https://moxt.ai)**（由「躺在废墟里」开发）启发——纸灰炭黑的两极色板、"标题写结论不写图型名"、"给没有真实记录的元素加交互是欺骗"这类判断，都是从那套数据可视化 skill 学到的。

概念结构图和数据图表的目的不同，有两处做了相反的选择：

- **不用单一强调色。** 数据图表有一个要讲的结论，拿一个强调色指向它是对的；概念结构图要讲的是整体结构，单一强调色会制造虚假的重点。所以改用三类分类色——颜色表达"属于哪一类"，不表达"有多重要"。
- **字号下限按中文定。** 常见的 6.5px 下限是给英文和数字的，中文笔画密，9px 才读得清。

本 skill 自包含，装上就能用。要画的是数据图表而不是概念结构图，去用 lieflat-charts。

## 不适用于

- 普通 PDF 转文字、摘要
- 纯数据图表
- 没有内在结构的文档（小说、新闻、流水账）——这套流程的前提是文档里藏着一个结构
