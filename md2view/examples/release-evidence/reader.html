发布成功，为什么用户还装不上？

这篇案例基于 coding-usage-bar 0.5.1 的真实发布复盘。读者是使用 Agent 维护开源工具的人：发布的目标，是让陌生用户从公开入口获得可工作的结果。

三种证据，回答三个问题

本地验证回答“代码在当前环境是否正常”。本次发布前通过了 139 项测试，并检查了构建和打包结果；这类证据不能证明公开安装已经可用。

分发验证回答“别人是否能拿到正确的包”。公开 registry 可读、安装命令能获取指定版本、取回文件与候选包一致，才证明分发路径成立。

使用验证回答“拿到包后能否完成任务”。命令可运行、菜单栏有实际内容、安装后的必要文件仍在，才是用户可见结果的证据。

命令成功与交付完成之间

本地验证通过后，先生成一个候选包。发布命令成功只表示 registry 已接收上传，并不代表公开安装立即可用。

这次发布经历了短暂的扫描等待。在公开入口读到指定版本以前，正确状态是“已接收，等待可用”；重复宣称完成不会缩短等待。

公开入口可读后，再用全新缓存和隔离安装目录取回包、执行核心命令。完成这一段，才可以把状态从“等待可用”改为“用户可安装”。

同一个包走到底

测试通过的候选包、发布到 registry 的包、GitHub Release 上的包，应当是同一份字节。验证后重新打一个包，会让原先的验证证据失去对应对象。

本次做法是只打包一次，保留 SHA-256；发布同一文件，再分别从公开 npm 和 GitHub Release 下载，对照哈希。哈希证明文件一致，不证明功能正确，所以仍需要使用验证。

安装行为也是产品的一部分

本次除了运行 CLI，还查看了实际菜单栏与运行时文件。看到一个安装命令退出成功，不足以推断后台任务、宿主插件或界面已经工作。

已有用户的配置需要保留。试用一个新 provider 时，能够只读查询就先只读查询；不要为了验证一行额度而改写其他 provider 的状态或现有安装。

失败以后，先确认失败在哪一段

如果本地测试失败，回到实现；如果指定版本尚不可读，检查分发状态；如果包可下载但命令失败，检查安装环境；如果命令成功却没有用户需要的结果，检查实际使用路径。

不要把“未知”写成零，也不要把一次成功扩大成所有环境都支持。无法验证的订阅账号、系统版本和使用场景，应当明确列出，等待对应证据。

发布之后还要知道什么

发布记录应当说明版本、公开入口、验证过的核心路径和剩余限制。用户反馈最好包含实际任务、失败步骤、预期结果与实际结果，并移除凭据和私人内容。

下一个运营动作是让独立用户完成同一个任务。是否愿意第二次使用，比维护者再做一张演示图更能帮助判断下一步投入。
