# 导演方法

这份文件管怎么当导演，`worlds.md` 管画面长什么样，`exemplar.md` 管结构。成片按这个顺序评判：**声音、节奏、镜头、导演**（主角的表演、布景、情绪起伏）。好看的单帧只是起点。

本文方法来自社区实测：Lemo Opuscar（MIT 开源的代码影片风格库）的导演手册，以及“Opus 5.5 做视频：原理、技术栈、实操”的拆解。

## 1. 简报：能问就问一次，不能问就用默认

- **能和用户对话时**，开工前用一条消息问完，之后不再问：
  - 想要什么效果，每个选项写上用什么技术，例如“暗场电影感 → three.js + 后期”“干净排版 → 网页”“手绘 → Canvas 笔刷”；
  - 必须出现的事实、名字或例子；
  - 手上有没有自己的素材（配乐、logo、照片、数据）；
  - 要不要先看分镜（默认不要）。
- **一句话、无人值守时**（`-p` 模式、用户只给了题目）：不问，全部用默认，并在 `PLAN.md` 里写明替用户做了哪些决定。

### 1b. 用户给了参考片：参考片就是验收标准

参考片的视觉语言压过本 skill 的一切默认（包括电影模式的“一个发光主体 + 辉光 + 大片暗场”）。实测教训：参考片是上万条无辉光的 1 px 发丝线、厚圆环带里塞满微型文字、镜头贴近裁切；第一版套了默认的琥珀辉光小球，用户一眼否决，“差距很大”。

1. 开工前拆参考片：均匀抽 6–10 帧看全貌，再**原尺寸裁切**中心细节（缩略图看不出线有多细、字有多小、有没有辉光）。
2. 把看到的写进美术指导卡：线宽与密度（多少条、几 px）、有无辉光、主体占画面多大、是否裁切、文字是装饰还是信息、调色。
3. 每次给用户看画面之前，并排比一次：`python3 <skill>/scripts/refcompare.py --ref 参考.mp4 --ours-video out/demo.mp4 --out out/ref-compare.jpg`（第三行是两边的原尺寸裁切）。密度、渲染（辉光/锐利）、构图、细节层四项都对上了才发。

**参考片竖屏、成片横屏**时，整帧并排只能比观感，比不了细节。比同一物理尺度下的量：线宽（px）、文字高度（px）、每 100 px 里的线数。用 `--ref-crop` / `--our-crop`（`WxH+X+Y`，原尺寸像素，不缩放）各自选一块有代表性的区域（例如都选环带的一段），脚本打印两边裁切区和每 100 px 的亮线数粗略密度：

```bash
python3 <skill>/scripts/refcompare.py --ref 参考.mp4 --ours-video out/demo.mp4 \
  --ref-crop 400x300+160+300 --our-crop 700x300+600+400 --out out/ref-compare.jpg
```

两边密度差 > 30% 就调密度（线数、粒子数、线宽），再比。

## 2. Treatment（写进 PLAN.md，在看示例代码之前写）

1. **三个候选结构**，每个写几行：一条旅程、前后对比、倒计时、一份清单最后翻转……写出选了哪个、为什么。对一个题目的第一反应通常是套路，开场画面、结尾和配乐的走向都从题目本身想。
2. **一句话梗概 + 起承转合**：开始是什么样，哪里发生转折，结尾和开头有什么不同。
3. **对标作品**：选 1–2 部给这个题目定标准的作品（纪录片、片头、广告、游戏，或用户给的参考片），写两行：
   - 学什么：构图、节奏、镜头语法、色彩逻辑、配乐结构；
   - 不学什么：角色、具体镜头、旋律、logo、字体。
   对标作品比后面任何规则都更能抬高质量。
4. **一个只有这种媒介能做的动作**，放在情绪最高点。例如墨晕开变成下一幕，一个字变成物体，镜头穿过物体表面进入下一层。
5. **砍掉多余的**：观众在缩略图尺寸能读懂的一个梗，胜过三个看不清的。一个节拍需要解释，就删掉它。

## 3. 证明画风：先出两个方向的关键帧，再做整片

用**真的绘图代码**（不是示意图）渲染两个方向，每个方向一张关键帧，最好就是招牌镜头。两个方向的美术指导要真的不同，比如“暗场微距 3D”和“纸艺长卷”。

```bash
node <skill>/scripts/render.mjs --html index.html --stills <t>      # 每个方向写一个镜头，各出一张
```

- 能对话：把两张图发给用户，等用户选定。
- 无人值守：按第 6 节的评分表给两张打分，选高的，把分数和理由写进 `PLAN.md`。

选定之后才写全片。方向错了，后面一个小时都白做。

**给能动的 demo，不只给静帧**：用户要判断的是流速、密度和节奏，静帧看不出来。方向定下前后各出一段 30–45 s 的无声 demo（`--range a:b`，`--subframes 1`，约 1 分钟渲完），把 mp4 路径直接给用户。

## 4. 声音是片子的一半

- **每个看得见的动作都有声音**：落地、翻页、切换、液体、点击、布料。声音要和材质对上，纸、木、金属、墨、玻璃各不相同。
- **三层**：环境声（风、室内、城市、水、机器）、拟音（跟动作走）、音乐。拟音和关键音效出现时，音乐压低。
- **至少两次真正的安静**（或接近安静）：放在转折或情绪高点之前。安静之后的第一个声音，应该是全片最重要的声音之一。
- **用声音做转场**，至少两次：下一场的声音提前进来（J-cut），或上一场的声音拖过切点（L-cut）。
- 写一张**声音设计表**：每一段的环境声、主要拟音、音乐状态（铺底、推起、安静、落下）。

### 4b. 配乐要为这支片子写，不能是循环底

脚本合成的默认底乐是 4 个和弦循环，压在环境声下面，用户会说“希望有配乐”——听不出它是配乐。默认底乐只当占位；成片照画面时间线写一首（`scripts/score_kit.py` 的乐器 + 母带，写法参考 `assets/cocoon/compose_score.py`，乐段结构跟着你自己的时间线写，不要照它的段落，读 `cues.json` 拿到画面事件的时刻）：

| 画面 | 音乐做什么 |
|---|---|
| 开场第一批元素 | 每个元素一个音（钢琴单音 + 混响），音和元素同时出现 |
| 洪流 / 展开 | 铺底渐强、琶音浮现，接一个**带通、逐渐打开**的 riser |
| 慢放 / 特写 | 退到低音持续 + 稀疏旋律，让位给拟音 |
| 积累 / 闭环 | 每小节多一层（贝斯 → 8 分琶音 → 16 分 → 弦乐），声音也“积少成多” |
| 转折前 | 持续音制造张力，然后整段静掉（hush），接全片最重要的一声 |
| 爆点 | 冲击 + 全和弦；画面有连锁事件（点亮波）就配一串随事件疏密变化的高音 |
| 希望 / 结尾 | 小调转大调，下行旋律，片名处一个长尾和弦 |

**不能听也要验**：模型听不到声音，用测量代替耳朵：`python3 <skill>/scripts/audio_check.py out/score.wav --out out/`。逐秒响度曲线要和上表的起伏一致（冲击处最响、hush 处最低、开场单音段明显更安静），频谱图里不能有大块的宽带噪声（`HISS`：全频白噪声 riser、嘶嘶的环境底都会报），不能削波。混音用 `mix.py --music out/score.wav`，成片再跑一次 `audio_check.py 成片.mp4 --mix`（成片里拟音持续、又经响度归一，最响段只比中位数高 2–3 dB 是常态，所以成片不查 `FLAT`，只查 `HISS`/`CLIP`）；横竖两版共用同一份 `cues.json` 和配乐，音画天然同步。交付时写明“听感未经人工试听”。

成片 `HISS` 出现在换章时刻（如 25 s、48 s 附近）时，先查框架自动加的换章 whoosh，不要先调环境声（`amb_gain` 数字不变就说明不是它）：`EX.run({ autoCues: false })` 关掉自动音效，或在配乐里给该时刻垫和弦。

**画面事件 → 配乐的标准通道**：配乐要冲击、裂缝、首批元素到达这类时刻时，页面设 `window.__events = { impact, crack, … }`（`EX.run` 之前），`render.mjs --cues-out cues.json` 把它原样写进 `cues.json` 的 `events`；配乐脚本读 `cues["events"]`（`assets/cocoon/compose_score.py` 优先读它，没有才回退到常量）。参数改了就重跑 `--cues-out` 和配乐，不用手改时刻。

## 5. 节奏与镜头

- **先定节拍网格再做动画**：`EX.tempo(bpm)`，切点、关键动作、字幕落在拍子上。不必每拍都切，留出看的时间。
- **快慢交替**：至少一次明显的加速或减速，给观众一次喘息（一个长镜头或一次停顿）。全片一个速度就是失败。
- **至少四种不同的镜头运动**，景别真的在变（远、全、中、近、特写）。2D 也有镜头：推、拉、视差、焦点转移、画中画。
- **一个让人记住的招牌镜头**：一镜到底、尺度揭示，或用媒介本身完成的转场。
- **转场长在媒介里**：翻页、刻线生长、墨晕开、穿过表面，全片用同一套转场语法。避免默认叠化和生硬切换。
- 关键时刻，主体至少占画面高度的三分之一，剪影清楚。

### 5b. 看得清的流速，积少成多

讲“逐渐形成”的题目（茧房、复利、习惯、污染、谣言），观众要能跟住**一个**元素，才看得出“多”是怎么来的。实测：恒定每秒 5200 条、屏幕速度约 3000 px/s 的流，用户说“太快太密，没有积少成多的感觉”。

- **量化检查**：渲两帧相隔 0.1 s 的静帧并排看。同一个元素要认得出来、位移 ≤ 约 100 px（屏幕速度 ≤ 1000 px/s，穿过画面 ≥ 2 s）。认不出来就是太快。
- **数量要有曲线**：开场几条能逐条看清（每条一个声音），然后指数涨到洪流；特写处放慢（0.4× 左右）、变稀；积累段随时间再涨。速率和速度都写成“出生时刻”的函数，帧依然是 t 的纯函数（`flow.js` 的 `makePool({ rate, speed })`）。
- **字幕和画面对齐的是“到达画面”的时刻**：元素出生后要飞 2–3 s 才进画，速率曲线要提前于字幕。
- **因果要一个一个看得见**：“点赞一条 → 茧多一缕丝”，就把每一缕丝绑到一条真实点赞线的到达时刻和方向上，不要按固定时间表自己长。

## 6. 导演评审：拼图打分，每项 ≥ 8 分才继续

每写完一批镜头，以及交付前，都做一次：

```bash
node <skill>/scripts/render.mjs --html index.html --sheet auto       # 9 个关键时刻拼成一张 out/keyframes.jpg
```

用 Read 打开拼图，当一个挑剔的导演，按下面 7 项打 1–10 分，写进 `REVIEW.md`（轮次、分数、问题、改法）：

| 项 | 8 分是什么样 |
|---|---|
| 开头抓人 | 前 2 秒就有一个让人想看下去的画面或问题 |
| 一眼看懂 | 每格的主体清楚、够大、够亮，离开字幕也知道在讲什么 |
| 美术统一 | 每格都守住美术指导：只用调色板，没有平涂卡通、白卡或杂色，光晕不发白 |
| 镜头与转场 | 景别和运动有变化，转场是设计过的，没有空白帧 |
| 节奏 | 快慢有起伏，字幕读得完，没有一帧塞太多东西 |
| 讲清楚 | 每章一个概念，有具体数字或名词，事实准确 |
| 震撼 | 至少有一帧让人想截图转发：一个发光的主体、一次尺度揭示、一个“这怎么做到的”时刻。放进社区作品集锦里不显得廉价 |

有一项低于 8 分，就改代码重来，最多三轮。三轮后仍不到 8 分的项，交付时如实说明。打分要严：给 9 分要说得出它比 8 分好在哪。

**别把示例再做一遍**：评审时和你读过的示例比 6 个方面（结构、开场、招牌镜头、镜头路径、配乐走向、结尾），至少 4 个要不同。

## 6b. 开拍前清单（来自一个镜头 12 轮迭代的实测：每一条都是原尺寸截图里才看得出的问题）

把功夫花在**被认真看过的次数**上，而不是镜头数量上。写每个招牌镜头之前过一遍：

1. **颜色空间**：在 sRGB 里定的颜色，进着色器前转成线性；否则整片发白、发灰。`cinema3d.js` 的渲染链已经处理，自己写着色器时要注意。
2. **主光要窄**：一盏窄主光，加一道轮廓光，再加画面里的实际光源（炉火、屏幕、窗）。宽而平的主光会让主体和背景糊成一片。
3. **粒子避开焦外**：火星、碎屑沿运动方向拉成短线，从主体向侧面和后方飞，不要朝镜头飞；落在焦外的亮粒子会糊成光条。
4. **运镜要大胆**：推镜一次至少推近一倍，并加一个从镜头前掠过的前景物体制造纵深。在运动中看，小幅推镜等于没推。
5. **慢动作要变速**：关键瞬间前降到 0.2–0.3 倍速，之后回升（`timewarp`）。全程同速的慢动作没有冲击力。
6. **景深跟主角**：焦点落在主体上，背景化成光斑；开场可以从背景拉焦到主体。
7. **开场不出画**：首帧就要有光、有主体，不要一片黑等东西进来。
8. **数字不重影**：运动模糊（`--subframes`）会把跳变的数字叠成“19⁶/₇”；变化的数字放在 DOM 层，或者在子帧之间保持不变。
9. **背景要可读**：中景要有能认出的结构（滚筒的叶片、豆床的边、窗框），不要只有一片暗雾。
10. **高潮要有戏**：裂开、爆开、点亮时，有碎块、有撕裂的边、有闪光、有镜头的震动和回弹，而不只是一条线亮了一下。

**评审预算**：1–2 个招牌镜头各做 4–6 轮原尺寸截图评审（每轮 6 张，对照参考帧逐张写出还差什么），其余镜头 2 轮。

## 6c. 评审模式：强模型看图，执行模型改

执行模型（sonnet 档）自己评审时，常常看得出“不好”（会诚实打 6 分），却不知道该改哪个参数，两轮也改不到位。把评审交给更强的模型：它只看图、只写指令，不写代码，花的 token 很少；写代码和渲染仍由执行模型做。实测：sonnet 无人值守出的片子经 3 轮这样的评审，从“满屏乱线、能量球爆点”提到“涡流细网、炸开式爆点”，自评从 6–7 提到 7–8，约 1 小时。

每轮流程：
1. 执行模型渲一组**固定时刻**的原尺寸静帧（每镜 2 张，轮与轮之间时刻不变，才能对比），附 `refcompare.py` 的裁切对比，lint 为 0。
2. 评审模型看原尺寸帧（不要只看缩略拼图），每次挑出 3–6 个最伤观感的问题，每个问题写成一条指令。
3. 执行模型逐条实现，回报**每条做了什么、实测数字**、做不到的原因；不渲全片，等评审放行。
4. 最多 3–4 轮。最后一轮评审放行后，执行模型直接出成片（配乐、混音、检查一次做完）。

**指令必须可测**。实测中，带目标数值和自检方法的指令几乎一次命中；只描述观感的指令（“像水流，不像渔网”），两轮都没改好。每条指令写成这样：

```
问题：<看到了什么，在哪一帧>（例：45 s 节点已 86% 变红，但灰边更多，画面仍以灰为主）
改法：<具体参数和目标值>（例：节点变红时，它的边同时从灰 0.36 换成红 0.32，灰边只留未感染节点之间的）
自检：<执行模型怎么自己量>（例：45 s 那帧，安全区里红色像素 / (红 + 灰) ≥ 60%，写进回复）
```

常用的可测量：
- 某元素包围盒占画面高度的比例；
- 亮度 > 40/255 的像素占比（太暗低于约 6%）；
- 某帧中心 1/3 区域里必须出现的东西；
- 红灰像素比；
- 0.1 s 两帧位移；
- 每 100 px 的线数（`refcompare.py`）；
- 节点数和人数曲线（让页面暴露数据，用 `--eval` 读）。

评审要守住的事：
- 一轮矫枉过正很常见（实测第 1 轮改完整片太暗），下一轮明确说“方向对了，保持 X，只改 Y”。
- 执行模型改了参数偏离指令时，要它写明为什么（例：按指令值灰线会被淹没）。理由成立就接受。

## 7. 先出 15 秒样片

全片渲染之前，先把开头约 15 秒连同声音完整做出来：

```bash
node <skill>/scripts/render.mjs --html index.html --range 0:15 --subframes 2    # → out/sample.mp4
```

再配上声音，按第 6 节检查一遍：开头抓不抓人，节奏、声音和运动模糊对不对。能对话就发给用户确认；无人值守就自己抽帧检查（`ffmpeg -vf fps=5,tile=…` 看关键动作的逐帧条），没问题再渲全片。

## 8b. 爆点：选一个时刻，做到有爽感、有新奇感

全片只选一个（通常是尺度揭示或转折的那一下），把功夫集中在这几秒。下面是结构，具体形态从你的题材里长出来：什么被积蓄、什么被撞开、后果怎么扩散，每个题材都不一样（茧被撑破、网络被点亮、冰面碎裂、多米诺倒下……），不要套用某个示例的形态：

1. **子弹时间**：冲击前约 1.5 s，世界自己的时钟降到 0.1–0.15×，画面里正在运动的东西悬停，主体蓄力（被挤压、被拉紧、被逼近）。实现：`flow.js` 的 `makeClock` 给出世界时钟，相机和特效用真实时间 t；冲击后世界时钟追回，后面的画面和声音照样对齐。蓄力那一帧要同时看到“将被撞的”和“正飞来的”，画面不能空。
2. **冲击**：主体有一个物理反应（弹开回弹、碎裂、爆散，带过冲和阻尼），一道锐利的冲击波，约 0.1 s 闪白（alpha ≤ 0.3），0.3–0.4 s 内衰减的震屏。不要用半透明的放射扇和同心圆，那会读成廉价的能量球。
3. **释放**：冲击那一刻镜头立即动（常见是火箭式后拉，先快后慢），被冻住的东西加速冲出；冲击后 0.3 s 内，后果要已经在画面里，不能只在画外。
4. **连锁**：后果从冲击点向外有先后地扩散（发生时间 = 冲击时刻 + 距离 / 波速），每个个体被波及时有一个小反应，观众能看出“一个接一个”。
5. **声音**：riser 收在冲击点、冲击 + 低频轰鸣，连锁配一串随事件疏密变化的音（时刻用 `window.__events` 传给配乐）。

检查：以 4 fps 抽这 6 秒拼成一张图，蓄力（几乎不动）→ 冲击 → 释放 → 连锁四个阶段要一眼分得出。

## 8c. 收尾：转折之后要有落点

转折一出现就结束，用户会说“结束得太突然，意犹未尽”。转折后再给 6–9 s：画面把转折延续成新状态（裂缝继续扩大、新的东西流进来、镜头缓慢后拉），一句收束字幕，然后**先压暗背景、清掉字幕（`caps` 里写 `[t, null]`，或给最后一句加结束时间 `[t, 文本, 结束]`），再出片名卡**并停住，音乐落在一个长尾和弦上。片名直接叠在亮画面上、或压着最后一句字幕，都会显得乱。

## 8. 最常见的失败

- 主体太小、太远，或贴在画面边上。
- 太暗看不清，或者同色叠同色（红底上的红字）。
- 字幕挡住主体。
- 一个梗或一次失败太快，观众没看懂。
- 转场里出现空白帧。
- 光晕太亮，画面发白。
- 一帧里画了太多东西。
- 渲染慢得离谱：在页面里逐帧画颗粒，或者 CSS `filter: blur` 用在会动的东西上。
- 跟随主体的效果（放大、聚光、跟拍）在相机移动后没跟上主体：屏幕坐标一律从同一个世界坐标换算出来。
- 没看参考片的原尺寸细节就出 demo，风格整体跑偏（第 1b 节）。
- 流太快太密，没有一个元素能被跟住（第 5b 节）。
- 特写里的信息看不清，或者只是编号和占位文字（`worlds.md` 的“数据艺术”）。
- 尺度揭示后的群像连成一张网，像大脑，看不出是一个个人（同上）。
- 会动或会变的文字在运动模糊下重影（天数、跟着线走的标签）：文字按视频帧定格。
- 转折后立刻结束；配乐是循环底，听不出是配乐（第 8c、4b 节）。
- 自己写级联 / 粒子时把 Float32Array 里的值和 double 比较：几乎恒真或恒假（级联一步都没扩散，只有一个红点）。比较前统一类型（`Math.fround`）或用 Float64Array（`assets/flow.js` 文件头）。
- 多个子系统共用一个 `rng(seed)`：改一个参数，整条随机序列移位，关键节点和配乐时刻全变。每个子系统用自己的 `rng(seed)`，并通过 `window.__events` 导出关键时刻。
- 配乐写好后成片换章处出 `HISS`：框架自动的换章 whoosh 撞上配乐低谷（第 4b 节），用 `autoCues: false`。
